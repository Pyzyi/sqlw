# Qualitätsmodell nach ISO/IEC 25010

Dieses Dokument beschreibt, wie die SQL-Werkstatt die acht Produktqualitätsmerkmale der ISO/IEC 25010 umsetzt und wie sie nachgewiesen werden.

**Zielgruppe:** eine lernende Person, die sich auf eine Klausur zu Datenaufbereitung und SQL vorbereitet und die Anwendung auf einem Heimserver (ZimaOS) betreibt.

## 1. Funktionale Eignung

| Teilmerkmal | Umsetzung | Nachweis |
|---|---|---|
| Vollständigkeit | Jeder Punkt der Lernzielliste ist durch Lerneinheit **und** Aufgaben abgedeckt (Matrix im README); das Übungsblatt aus dem Unterricht ist vollständig enthalten; ein Test prüft die Abdeckung jedes Lernziels. 199 Aufgaben in 9 Typen. | Abgleich README-Tabelle ↔ Lernzielliste |
| Korrektheit | Bewertung durch echte Ausführung (SQLite/WASM) und Vergleich mit der Musterlösung: Spalten- und Zeilenanzahl, Werte (Zahlen auf 2 Stellen normiert), Reihenfolge nur wenn die Aufgabe `ORDER BY` verlangt, Gleichstände über `orderKeys`, Aliase wo gefordert. DML-Aufgaben vergleichen den Datenbestand nach der Änderung. | `tests/content.test.mjs`: jede Musterlösung besteht, jede Fehler-finden-Startabfrage fällt durch, jede Vorhersage stimmt mit der Engine überein, DML ändert den Bestand, die Ergebnisse des Übungsblatts stimmen mit einer Handrechnung überein |
| Angemessenheit | Feedback nennt die konkrete Abweichung („3 Spalten erwartet“, „falsche Reihenfolge – ORDER BY?“), SQLite-Fehler werden ins Deutsche übersetzt und mit Ursache erklärt. | Test „Bewertung erkennt typische Fehler“ |

## 2. Leistungseffizienz

- Keine Framework-Laufzeit, kein Build-Schritt; App-Code inkl. aller Inhalte ca. 200 KB JavaScript (gzip ca. 60 KB).
- Größter Brocken ist die SQLite-Engine (660 KB WASM) – vom Server einmalig gzip-komprimiert, danach `immutable` gecacht.
- Jede Aufgabe läuft auf einer frischen Kopie, die per `Database(bytes)` aus einem Speicherabbild erzeugt wird (< 1 ms), statt das Seed-SQL neu auszuführen.
- Container-Limit 128 MB RAM / 0,5 CPU; Leerlaufverbrauch eines Node-Prozesses ~40 MB.

## 3. Kompatibilität

- Läuft in allen aktuellen Browsern (Chrome, Firefox, Safari, Edge; Desktop und Mobil).
- Docker-Image für `linux/amd64` und `linux/arm64` (ZimaBoard, ZimaBlade, Raspberry Pi).
- Koexistenz: ein Port, ein Volume, keine Host-Abhängigkeiten.
- SQL-Dialektunterschiede (LIMIT/TOP, `||`/CONCAT, `strftime`/`DAYOFWEEK`) sind in den Lerneinheiten benannt, damit das Gelernte auf das Klausur-SQL übertragbar ist.

## 4. Benutzbarkeit (Interaktionskapazität)

| Teilmerkmal | Umsetzung |
|---|---|
| Erkennbarkeit | Übersicht zeigt sofort „Weiterlernen“, Klausurreife, fällige Wiederholungen, Tagesplan bis zum Klausurdatum |
| Erlernbarkeit | Jedes Modul: erst Lerneinheit mit **editierbaren, ausführbaren Beispielen**, dann Aufgaben steigender Schwierigkeit; Schema-Panel, Zielergebnis und Hinweis je Aufgabe |
| Bedienbarkeit | Tastenkürzel (Strg+Enter ausführen, Strg+Shift+Enter prüfen), Schnelleingabe-Leiste für Mobilgeräte, Klick auf Spaltennamen fügt sie ein, Entwürfe werden automatisch gespeichert |
| Schutz vor Fehlbedienung | Destruktive Aktionen (Zurücksetzen, Klausur abbrechen) mit Bestätigung; jede Aufgabe läuft auf einer Kopie – die Übungsdatenbank kann nicht „kaputtgehen“ |
| Ästhetik | Eigenes Designsystem (Papier/Tinte/Signalorange, Fraunces + IBM Plex), Hell- und Dunkelmodus, keine generischen UI-Kits |
| Barrierefreiheit | Semantisches HTML, Skip-Link, Fokusrahmen, `aria-live` für Feedback, `aria-pressed`/`aria-current`, Kontraste ≥ 4.5:1 für Text, `prefers-reduced-motion` respektiert |

## 5. Zuverlässigkeit

- **Verfügbarkeit:** `restart: unless-stopped`, Healthcheck auf `/api/health`.
- **Fehlertoleranz:** Ist der Server nicht erreichbar oder das Datenverzeichnis nicht beschreibbar, arbeitet die App mit dem Browser-Speicher weiter. Laufende Probeklausuren überstehen einen Seiten-Reload.
- **Wiederherstellbarkeit:** Lernstand wird atomar geschrieben (temporäre Datei + `rename`), Export/Import als JSON, Volume-Backup im README beschrieben.

## 6. Sicherheit

- Strikte **Content-Security-Policy** (`default-src 'self'`, kein Inline-Script, nur `wasm-unsafe-eval` für die Engine), `nosniff`, `no-referrer`, `frame-ancestors 'self'`.
- Keine externen Ressourcen (Schriften und Engine lokal) – keine Datenweitergabe an Dritte.
- Alle Benutzereingaben werden vor dem Rendern escaped; SQL läuft ausschließlich im Browser in einer Sandbox-Datenbank.
- API: Profilnamen per Whitelist-Regex, Pfad-Traversal-Schutz, Body-Limit 1 MB, nur `application/json`.
- Container: übernimmt beim Start nur den Datenordner und läuft danach als unprivilegierter Benutzer (UID 1000) ohne Capabilities; `read_only`-Dateisystem, `cap_drop: ALL` (nur `CHOWN`/`SETUID`/`SETGID` für den Start), `no-new-privileges`. Die Rechteabgabe wird in der CI im echten Container geprüft.
- Hinweis: Die API hat keine Anmeldung und ist für den Betrieb im **Heimnetz** gedacht. Für Zugriff aus dem Internet einen Reverse-Proxy mit Authentifizierung (z. B. Authelia, Cloudflare Access) davorschalten.

## 7. Wartbarkeit

- **Modularität:** Inhalte (`content/`), Engine, Zustand, Ansichten und Server sind getrennt; Inhalte sind reine Daten.
- **Wiederverwendbarkeit:** Ein Aufgaben-Renderer für Lernen, Wiederholung und Klausur.
- **Analysierbarkeit/Prüfbarkeit:** Automatisierte Tests (`npm test`) und ein Container-Integrationstest (`e2e/container-test.sh`: Bind-Mount, Rechteabgabe, Persistenz) in der CI auf jedem Push.
- **Änderbarkeit:** Neue Aufgaben ohne Code-Änderung; die Übungsdatenbank wird deterministisch generiert (`npm run seed`).
- Keine npm-Abhängigkeiten → keine Abhängigkeits-Updates, keine Supply-Chain-Risiken.

## 8. Flexibilität (Übertragbarkeit)

- **Installierbarkeit:** Fertiges Multi-Arch-Image aus GHCR, Installation per ZimaOS-Import (`docker-compose.yml`) oder lokaler Build (`docker-compose.build.yml`); ZimaOS-/CasaOS-Metadaten (`x-casaos`) enthalten.
- **Anpassbarkeit:** Port, Zeitzone und Datenpfad per Compose/Umgebungsvariablen.
- **Ersetzbarkeit:** Läuft auch ohne Docker (`npm start`) oder rein statisch (dann ohne Geräte-Sync).
